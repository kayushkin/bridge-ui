# About bridge-ui

## What it owns

A React and TypeScript library, not a service: no port, no database, no deploy of its own. `@kayushkin/bridge-ui` is the whole user interface over an llm-bridge-server backend as one component — `<Bridge>` routes every page, draws the navigation, and mounts both providers: `BridgeProvider` for config and chat-core's `ChatProvider` for the session store, held above the router so switching tabs does not drop it. It is published source-only (`main` is `dist/index.js`, `files` ships `dist`, `styles.css`, `theme.css`, `zine.css` and `zine/`) and consumed through a `file:` link; dash is the host that mounts it. `README.md` is the mounting guide: the props, the two stylesheets, and what a host wires.

llm-bridge-server contains no `go:embed` and does not serve this library; dash is the only surface that serves it today.

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

# How it works

## The page registry

**Every page this library ships is one row of `BRIDGE_PAGES` in `src/pages.ts`** — a `route` key into `BridgeRoutes`, a `label`, a navigation `group`, whether it is `listed`, and optionally `end` (the chat, which sits at the root and would otherwise look active everywhere), `routeSuffix` (`/:cardId`) and `available(config, flags)`. `<Bridge>` builds both the `<Route>`s and the navigation from that list, so **a page is added in one place**.

The pages, by group, with the config field that makes each available:

- **Work** — Chat (`end`), Sessions, Kanban (`kanbanStoreBasePath`), Board settings (routed, not listed), Card (`/:cardId`, routed, not listed), Email tickets (`kanbanStoreBasePath` and `mailBasePath`; each email ticket beside the email its `source_entity_ref` names), Orchestrator (`orchestratorBasePath`), Previews (`previewsBasePath`; the dev servers agents are running, each in a frame, `?port=` picking one).
- **Messages** — Waiting on you (`/messages/waiting`, first, so the group's tab opens it; a count badge on its tab and on the Messages group tab — `BridgePage.badge`): conversations where someone the operator tagged wrote after their last word, read from multichat's `GET /awaiting-reply` by one shared 15-second poll (`useAwaitingReply`), with a Cleared list and `?settings=1` for its two settings sections — who counts (multichat, scope `global`) and sound and pop-ups (localStorage, scope `browser`); opening a waiting room on that page or in the chat posts `POST /awaiting-reply/clears`. The chat sidebar shows the same list under the Orchestrator row (`components/chat/AwaitingReplySidebarSection.tsx`), and a row opens the room where the thread is (`?view=conversation&room=`, `ChatConversationPane`, reusing Conversations' exported `ConversationThread`). `AwaitingReplyAlerts`, mounted by `BridgeLayout` on every page, plays a synthesised sound (`src/alertSound.ts`) and shows a pop-up for each new arrival except the room on screen; clicking one opens it in the chat's pane through `chatConversationEvents.ts`, or on the Waiting on you page elsewhere. Rules in `src/awaitingReply.ts`. Conversations (`/messages` and below; rooms on different apps linked as one conversation — multichat's `/conversations/links` — list as one row, and opening it shows a tab per room above the thread, with "Same conversation" under the room's name to link it with another chat or unlink it (`conversationEntries` in `src/multichatMessages.ts`); multichat marks each room `hidden` — by the operator's choice, or by its auto-hide rule above a member count (30 by default) — and the list leaves hidden rooms out unless **Show hidden** is ticked; "In the list" under an open room's name sets Auto, Hide or Always show, and the rule is edited beside the toggle (`conversationVisibilityReason`); `/messages/<short name>` (one to three segments: `/messages/kat`, `/messages/20s30s/general`) opens the room short-name-store names in namespace `messages` (`shortNameStoreBasePath`; rules in `src/messageShortNames.ts`) — a superseded name is replaced in the URL by the current one, an unknown one says no chat is called that, and the sub-pages' literal routes win over the name; picking a room puts its current name in the URL, and the thread header shows it as `messages/kat` with a rename control that posts a new name and shows the store's refusal verbatim; linked rooms show the name of whichever room in the link has one; `?room=` opens a room by its id, which is how a room with no name yet is addressed and wins over the path, and an old `?room=` link to a named room moves to the name. An open room is one to read, page back through, send into and react in: a toolbar that shows beside each message's bottom corner on hover holds the first favourites as one-click reactions and a react button that opens the emoji panel above the composer, and a reaction chip adds ours or takes back the one we posted — `reactionChipAction` in `src/messageReactions.ts`; images and other files are pasted into the text box, dropped on the thread or picked with 📎, wait above the box with a preview, and go one message each through multichat's `send-file` with the typed text as the first one's caption (`src/messageAttachments.ts`); a received image opens large in the page, a video or audio file plays in place, and a caption shows under its file; in the text box `:` and two characters open name suggestions, and a draft of `+:name:` or `+` and an emoji reacts to the newest message instead of sending), Search (`/messages/search`, `?q=`) and Contacts (`/messages/contacts`, with multichat's tags), all gated on `multichatBasePath`. The host's proxy must forward every route `MULTICHAT_ROUTES_CALLED` in `src/multichatMessages.ts` lists; a send there reaches a real person. Emoji (`/messages/emoji`) sets the favourites, skin tone and quick-reaction count, shows whether the Discord account has Nitro (with Check now), lists the custom emoji of every server the account is in (grouped by server id) and the ones seen in messages, shows how far multichat's weekly listing of those servers has got (re-read every 30 seconds while it runs) with a button to start it now, and refreshes the bridged servers with the bot (multichat's `GET /emoji` and its writes). - **Agents** — Instances, Agents, Files, Skills (`skillStoreBasePath`), Tools (`toolStoreBasePath`), Bundles (`bundleStoreBasePath`), Hooks, Inbound rules (`multichatBasePath`).
- **Access** — Principals (`principalStoreBasePath`), Grants (`grantStoreBasePath`), Permissions (`permissionStoreBasePath`), Auth, Peers (`/peers`: other llm-bridge-servers this one is connected to — each connection's transport, direct or dial-out, and whether its socket is open; the access the other gives this one, with Check; Remove with a reason; then making a connection, either as the side with an address — a one-time passphrase shown once beside this server's `public_url` setting, read from its own `/settings` — or as the side entering the other's address, where leaving this server's own address empty makes it dial out; the page says that an unmapped person is refused and that an administrator there acts as the whole server; every route is an operator route), and Connected server (`/peers/:connectionId`, routed, not listed): that server's sessions through `{basePath}/peer-connections/{id}/proxy`, which goes direct or over the socket, under a second chat-core `ChatProvider` with `cache={false}` and `keepDraftsAndFiltersInBrowser={false}` and a `BridgeConfig` whose every other path is emptied (`peerConnectionBridgeConfig`), since this host's stores know nothing of the other server's ids; it says first, in plain words, when the connection is removed, holds no access or has its socket closed; then a list, `TurnList`, a plain composer and New on one of its instances.
- **System** — Settings, Usage, Effective config, Service settings, Models (`modelStoreBasePath`), Service inventory (`showServiceInventory`), Conformance (`showConformance`).

A page that is not available is **still routed**, so a stale link lands on a page that says what is missing rather than on nothing; it is only left out of the navigation. `PAGE_GROUPS` is the group order: Work, Messages, Agents, Access, System, Personal. Personal holds no page of this library's own — it is there for the host's pages.

## The two-row navigation and the host's slots

The navigation is two rows: `nav.bridge-nav-groups` holds the groups, `nav.bridge-nav-pages` the listed pages of the group the current path belongs to. `groupForPath(pathname, routes, hostPages)` picks that group by the **longest route that is a prefix of the path**, listed or not, so a sub-page such as a card lights up Work with no tab pointing at it. `navEntriesFor(config, flags, hostPages)` returns the entries: this library's listed and available pages in registry order, then the host's.

The group row sits in one `<header class="bridge-shell-bar">` with two host slots — **`<Bridge navStart navEnd>`**, the host's brand before the groups and its own controls after them — so **a host draws no header of its own**. **`<Bridge hostPages>`** takes the host's pages (`path`, `label`, `group`, `element`, optional `end`), routes them beside this library's and lists them in the same two rows, so a host has one navigation rather than two bars.

## Every setting is a SettingsSection

`src/components/settings/SettingsSection.tsx` is the one frame for a stored setting, exported from the package index. It draws a **scope badge** — `SettingsScope` is `global` | `harness` | `instance` | `board` | `principal` | `session` | `browser` (kept in this browser's localStorage), labelled by `SETTINGS_SCOPE_LABEL` — the service and record that store the value (`storedBy`), a one-line `precedence` note, a per-section save, and the store's refusal **verbatim** (`SaveResult` is `{ok:true}` or `{ok:false, error}`; `useSectionSave` and `saveResultOf` wrap a write).

A narrower scope overrides a wider one: session over board over instance over harness over global. `SETTINGS_SCOPE_INDEX` says where each scope is edited and opens the Settings page, so a person looking for a per-board setting is sent to the board settings page instead of hunting. The kanban board settings page uses the same frame, section by section. A new setting goes in a `SettingsSection` on the page of the thing it applies to — not in a form of its own.

**A service's own configuration is not one of those: it is drawn, not written.** `/service-settings` (System group, `BridgeServiceSettings`) asks every backend the host proxies for `GET {base}/settings` — llm-bridge's `msg.ServiceSettings`, served by its `servicesettings.Handler` — and draws whatever answers: each setting with its environment variable, the value in force, and whether the environment, the service's stored record or a built-in default decided it. A behaviour setting the service stores gets a Change button (`PUT {base}/settings/{key}`, the refusal verbatim, the page redrawn from the service's answer); wiring, paths and secrets are read-only, and a secret shows only `set` or `not set` because the service never sends its value. A backend that answers anything else is listed as *does not describe its settings* — that list is what is left to convert. A setting whose `value_type` is `model_role` names a model-store role, not a model: it is edited with a drop-down of model-store's `canonical` roles from `GET {modelStoreBasePath}/api/roles`, each shown with the models it resolves to (`useModelStoreRoles`). The page hardcodes no setting of any service; `src/serviceSettings.ts` holds its pure rules (which base paths to ask, grouping by the kinds the service served), tested. To make a service appear, give it a `/settings` route; nothing changes here.

**Models** (`/models`, `BridgeModels`) reads the same services through the same `fetchServiceSettings` and `putServiceSetting` and gathers every `model_role` setting into one *Background calls* table — service, setting, role (saved through that service's `PUT /settings/{key}`) and the models the role resolves to. Its *Roles* section edits each canonical role's ordered list (reorder, add an enabled model with its provider and price, remove) and saves it whole with model-store's `POST /api/roles {"role","models"}`, showing a refusal's text. The first model is used; the rest are tried in order when a call fails. No role or model is named in the code: roles come from `canonical`, models from `GET /api/models`. Rules in `src/modelRoles.ts`.

## The Files page and the prompt source

`BridgeFiles` (`/files`) lists every file agent-store's scan tracks, and carries `PromptSourcePanel` (`src/components/PromptSourcePanel.tsx`) above it: the prompt collections, their sections, the files they render to, the drifts waiting to be carried back, and each harness's delivery. It reads `{basePath}/prompt-collections` and `{basePath}/prompt-delivery-options`. Its tabs are the host prompt, the project prompts and **ticket context** — agent-store's `context` collections, which render to no file and whose sections a session gets when its card carries every one of a section's tags. The panel creates a context collection (`contextCollectionCreateBody`, a blank root for every directory), shows it even while empty, hides the output and render controls for it, and the harness preview takes card tags (`contextResolveQuery`, kept as typed by `parseCardTagInput` because the match is exact) and lists which sections they select and why the rest were left out.

**A file that a collection renders is read-only in the file list.** The panel hands the page its collections through `onViews`, `renderedOutputsByPath` turns them into a lookup by path, and a file found there is drawn with a `rendered from …` tag, its content in a `<pre>` rather than a textarea, and an **Open its sections** button that scrolls the panel to that collection (`openCollection`, with a `nonce` so asking twice counts). The note beside it says the file is changed in its sections, and that an edit made to the file itself is still picked up by the next scan.

`src/promptSource.ts` holds the wire types and the pure rules — `promptOutputState`, `collectionNeedsRender`, `groupSections`, `filterSectionGroups`, `describeDriftOperation`, `sectionWriteBody`, `renderedOutputsByPath`, `collectionsForTabs`. **Nothing there names a prompt file or a harness**: file names and delivery kinds come from `GET /prompt-delivery-options` and harness ids from `GET /prompt-harness-deliveries`, because a copy here would go stale the day a harness is added.

## One renderer for a chat message's content

`src/components/messages/MessageContent.tsx` draws a message's content on Conversations and on the Discord page's Messages and Deleted tabs (Search shows multichat's plain hit text). `format` picks the renderer: `org.matrix.custom.html` → `formatted_body` through `sanitizeMatrixHtml`, `discord-markdown` (archive rows) → react-markdown, gfm and `remarkDiscordInline`, anything else → plain text with its newlines. A message with `media_url` is an image thumbnail (`/media/S/I?width=&height=`) linking to full size, or a link for any other file. **The sanitizer is an allowlist walker, not DOMPurify, and no message HTML ever reaches `innerHTML`**: the browser's `DOMParser` builds an inert document, the walker keeps the Matrix spec's tags with a handful of checked attributes, drops `<mx-reply>`, scripts and every `on*`/`style`, keeps only `http`/`https`/`mailto` links (new tab, `noopener`), and keeps an `<img>` only when its `src` is a valid `mxc://` URI, rewritten to multichat's media route. Its output is a plain tree that React turns into elements. `test/messageBody.test.ts` runs it over linkedom's parser with script, `onerror` and `javascript:` payloads.

The emoji pickers (`EmojiPicker.tsx`) read two sources. Unicode emoji come from `src/emojiData.ts`, **generated** by `node scripts/generate-emoji-data.mjs` from the `unicode-emoji-json` devDependency (emoji version 15.0 and older, ~1,870 emoji, each marked when it takes a skin tone) and loaded by a dynamic `import()` the first time a picker opens, so the page bundle does not carry it. Custom Discord emoji, favourites and settings come from multichat's `GET /emoji`, loaded once per page and shared by every picker through `useEmojiCatalog`. A reaction can be any emoji the room is offered; a custom one is posted as `discord-emoji:<id>` and multichat answers the `mxc://` key it reacted with. **A custom emoji cannot go inside a message**: the Discord bridge escapes `<` and drops `<img>`, so the composer's picker leaves custom emoji out and its `:` suggestions show them greyed with that reason. A pick in the composer only goes into the text box.

## Generated store types, never hand copies

**Every store wire type comes from that store's own generated package**, all `file:` links to the store's main clone: `@kayushkin/kanban-store-types`, `noteboard-types`, `principal-store-types`, `grant-store-types`, `bundle-store-types`, `tool-store-types`, `repo-store-types`, `work-graph-store-types`, `project-store-types`, `photo-store-types`, `multichat-types` and `llm-bridge-types`, plus `@kayushkin/chat-core` itself. Do not restate a store's record as a local interface; if a field is missing, fix the Go struct and re-run that repo's `./generate-ts.sh`.

A vocabulary the store serves is **derived from the record field**, not written out as a union: `GrantResourceType = Grant['resource_type']`, `PrincipalKind` the same way.

Three types are still hand-written, each with the reason in its file: `src/types-model-store.ts` (model-store has no generated package yet), `src/types-mailstack.ts` (`MailMessage`, deliberately partial — `body_html` is left out so no caller here can render an attacker-controlled body) and `src/types-multichat.ts` (multichat's unified contact list, search answer and tags, which its router assembles from unnamed types, so tygo has nothing to render; and its conversation, message and message-page records, which are named structs in `internal/matrix/client.go` that multichat's `tygo.yaml` does not render yet — render them there and these copies go).

Because each package is consumed through the store's main clone, **a store whose `ts/package.json` is missing breaks `tsc` here, loudly** — check the sibling repo before blaming this one.

# Access and operations

## What a host must proxy, and what it can switch off

The host passes a `fetch` that carries its own credentials and a base path per backend; `src/context.ts` is the list. `basePath` is llm-bridge-server and is always needed. The rest gate the pages named in the registry: `skillStoreBasePath`, `toolStoreBasePath`, `permissionStoreBasePath`, `kanbanStoreBasePath`, `principalStoreBasePath`, `grantStoreBasePath`, `bundleStoreBasePath`, `orchestratorBasePath`, `multichatBasePath`, `shortNameStoreBasePath` (the Messages page's typeable chat names; without it rooms are addressed only by `?room=`), plus `repoStoreBasePath`, `noteboardBasePath`, `usageStoreBasePath`, `mailBasePath` and `bridgeAdapterBasePath` used inside pages. Seven more are read only by `/service-settings`: `schedulerBasePath`, `logStoreBasePath`, `jobStoreBasePath`, `quoteStoreBasePath`, `predictionStoreBasePath`, `eventStoreBasePath` and `authStoreBasePath`, and `hostBasePath` for the host's own settings (dash serves them at `/api/dash/settings`). `previewsBasePath` is the host's list of ports agents' processes listen on (dash: `/api/previews`), read by `useDevServerPreviews` (`src/useDevServerPreviews.ts`), which polls once every 5 seconds however many components read it. It gates the Previews page and the **View :port** link `BashRenderer` draws on a Bash call whose command or output names a local URL (`localPortsMentioned` in `src/devServerPreviews.ts`) that is in that list. The host decides what the list holds and which public port shows each server; this library only frames `previewUrl`, the page's own hostname on that port. `workGraphStoreBasePath` is work-graph-store (dash: `/api/work-graph`), read by the chat's `?view=work-graph` (`components/chat/WorkGraphView.tsx`): one repo's commit graph with each commit's dot in the colour of the session that made it, opened from the sidebar's pinned Work graph row and the Orchestrator's header. `modelStoreBasePath` is model-store (dash: `/api/model-store`, which roots its API at `/api`), read by the Models page and the `model_role` drop-down. `projectStoreBasePath` is project-store (dash: `/api/projects`), read through one shared poll (`src/useProjectStore.ts`: `GET /projects` and `GET /links?entity_type=session`, re-read after every filing) by three things: the chat's `?view=projects` (`components/chat/ProjectsView.tsx`; `&project=` opens one project's page, and the chat's URL effect writes both params), opened from the sidebar's pinned Projects row; the sidebar's **Group by project** toggle (localStorage `chat:group-by-project`, default on); and the session header's filing control (`SessionProjectControl.tsx`), which writes the new link before deleting the old one. A project id in a message is a chip because chat-core detects every id pattern the host's resolver lists (`useResolvableIdPatterns`), and a resolved project draws as `ProjectRefChip`. `peopleStoreBasePath` and `journalStoreBasePath` (dash: `/api/people`, `/api/journal`) are read only by `/service-settings`; a resolved `person_…` or `entry_…` id draws as `PersonRefChip` or `EntryRefChip` (rules in `src/journalRefs.ts`), whose panel links to the host's own page, `peoplePagePath` or `journalPagePath` plus `?id=`, and shows no link when the host passes none. An entry chip never shows the entry's body: it is private writing, and a chip can sit in a chat an agent reads. A `message_…` id (multichat's message log, kanban-store type `message`) draws as `MessageRefChip`: sender and day on the chip, and the chat, app, time and text in its panel, with an Open conversation link to `routes.messageConversations?room=` (rules in `src/messageRefs.ts`). A `photo_…` id (photo-store, type `photo`) draws as `PhotoRefChip`: a small thumbnail and the day on the chip, and in the panel the picture, when it was taken and how sure (`date_source`), the folder, the description and a map link when it has GPS; the thumbnail comes from `photoStoreBasePath` (dash: `/api/photos`) + `/photos/{id}/thumbnail`, and an empty base path draws a 📷 instead (rules in `src/photoRefs.ts`). An empty base path hides its page from the navigation and its panels from the pages that would use it.

Two switches are the host's, not a store's: `showConformance` and `showServiceInventory` (`ShellFlags`). **Service inventory reads `GET /services` on `basePath`**, the bridge server itself, so no store path gates it; a host whose server lacks the route turns the tab off instead.

# Working in this repo

## Build, packaging and how a change goes live

`npm run build` is plain `tsc` plus `node scripts/copy-css.mjs`, which copies every `.css` under `src/` into `dist/` at the same relative path — `tsc` emits no CSS, and without the copy a component's relative stylesheet import resolves to a file that is not there in the consumer's bundler. The package is ESM-only and ships `dist/`, `styles.css` (component styles, which only consume theme variables) `theme.css` (an optional default theme; a host with its own palette skips it) and `zine.css` (the zine skin, under `data-theme="zine"`, with its fonts and its pictures in `zine/`).

**`dist/` is not committed** — it is in `.gitignore`, `prepare` builds it on `npm install`, and every host's deploy rebuilds every linked library before bundling. **There is no deploy here.** A change goes live by deploying **dash**, whose `deploy.sh` runs `scripts/build-linked-libraries.mjs` and then `npm run build`. `standalone/` is a Vite launcher for local work (`npm start`), and its output is ignored too.

## Tests, the render check and the browser canaries

`npm test` is vitest over `test/**/*.test.ts` in the `node` environment. `vitest.config.ts` sets `resolve: { dedupe: ['react', 'react-dom'] }`, and that is load-bearing: `@kayushkin/chat-core` is a `file:` link with its own `node_modules`, so without it a context chat-core creates is built by *its* copy of React and read by ours — `useContext` on a null dispatcher. The hosts' Vite configs carry the same rule.

`npm run check` is the older render check: esbuild bundles `scripts/render-check.mjs` (which is why it can import `.ts`/`.tsx` from `src` directly) and node runs it, asserting on markup from `react-dom/server`. It proves what a component renders for a given input, not that the app wires that input up.

Three live browser canaries prove the wiring `tsc` cannot: `scripts/kanban-signal-canary.mjs` (signals in the card drawer, and that clicking an action posts the right verb), `scripts/sticky-bottom-canary.mjs` (the bottom pin across a session switch) and `scripts/timeline-window-canary.mjs`. They run against the standalone dev server or against dash with a token.

## Pruning orphaned CSS

`node scripts/prune-orphaned-css.mjs` reports every rule in `styles.css` whose classes nothing live references; `--write` rewrites the file. "Live" is this package's `src/`, `scripts/` and `test/`, dash's `src/` and `e2e/`, and chat-core's `src/`.

It parses the stylesheet with postcss rather than grepping, and that is the point: a class counts as referenced if its exact name appears, **or** if it begins with a prefix some template literal builds — the `bc-foo-${state}` sites would otherwise lose their styling silently. A rule with several selectors keeps the ones that survive; a rule with none goes, together with the comment that introduced it.

## Traps

- **Navigation tabs must stay `draggable={false}`.** A link is draggable by default. A tab pressed while the mouse moves starts a link drag, and a tab removed mid-drag — choosing a group replaces the second row — never gets its `dragend`, which on Chrome for Windows leaves the page taking no clicks while its timers still run. Both rows set `draggable={false}` in `BridgeLayout.tsx` and `-webkit-user-drag: none` plus `user-select: none` on `.bridge-tab`. Held by dash's `e2e/nav-tabs-are-not-draggable.spec.ts`.
- **The service inventory is not at `/services`.** dash's own Topology page owns that path and matches before the bridge's splat, which is how the first cut of that tab shipped unreachable.
- **The Sessions page shares chat-core's filter.** It reads chat-core's session store and its `FilterState` through `useFilters` and `useSessionList`, so filtering there filters the chat sidebar too, by design. Its dropdowns are single-select over multi-select axes.
- **A write must check `res.ok`.** `serverPrefsBackend.save` in `src/bridgePrefsStore.ts` throws on a non-OK `PUT`; a form that ignores the status reports a refusal as a success.
- **Two stylesheets, one theme.** `styles.css` defines no theme variable; a host either imports `theme.css` or sets the same variables at `:root`.
- **The zine skin lives here, and dash imports it.** `zine.css` is the one copy: the variables under `[data-theme="zine"]` plus rules on bridge-ui's own class names and on the hooks bridge-ui leaves for a skin — `.bc-status-mascot` (empty, drawn by `data-mood`), `.bc-conductor-mascot` (by `data-state`), `.bc-composer-sent`. A change to a class or hook a zine rule names is a change to `zine.css` in the same commit. The pictures in `zine/` are painted by code in the `zine-art` repo (`~/repos/zine-art`), which writes each piece to the repo that uses it (`BRIDGE_UI_PIECES` in its `pieces.js`); do not edit them by hand. `light` and `dark` must look the same with `zine.css` imported: every rule in it is scoped to `[data-theme="zine"]`, except the raw `--zine-*` inks at `:root` and the font faces.
